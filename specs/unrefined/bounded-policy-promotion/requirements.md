## Bounded policy promotion — Requirements

> Unrefined. Run /refine-spec bounded-policy-promotion before /spec.

> Promote immutable runtime data policies for a defined cohort only after protected evidence, current route qualification and applicable authority; canary future admissions, preserve running episode pins and reconcile bounded rollback. Normative source: `mythhelm-synthesis/MYTHHELM_Master_Spec_v2.md`, version 2.0, §§4–5, 7–13, 17–19; implementation slice W12 in `mythhelm-synthesis/MYTHHELM_Implementation_Plan.md`. Every I-ID below refers to v2 §2, every AT-ID to v2 §18.2 and every G-ID to v2 §18.3. Named checks are prospective requirements, not passing results or live qualification. This capture authorizes no activation, experiment, installation, native/provider call, collection or publication.

A useful learner can recommend retaining P1, reject a misleading improvement or report an inconclusive comparison. Promotion is a separate deterministic decision, with separately applicable authority, against the exact protected cohort and current qualified route facts. Faster execution cannot compensate for weaker acceptance, wider permissions, different funding or lost provenance. Promotion changes bounded data; executable and evaluator changes retain normal reviewed release governance (v2 §§12–13; W12).

A new model may make a whole pipeline unnecessary. Compare its qualified P1 workflow with the complete incumbent pipeline and strongest simpler baseline, including verification, interventions and all auxiliary costs. Metadata discovery alone supplies neither availability nor entitlement. If no useful live improvement is established, fixed-policy delivery remains useful and adaptive promotion remains experimental (v2 §§12.4–13.3).

## Objectives

- **O1**: Explain exactly why a scoped data-policy proposal is eligible, rejected, inconclusive or awaiting authority, without treating its evidence as authority.
- **O2**: Activate only authorized, qualified, protected improvements for future admissions while preserving running work and recoverable history.
- **O3**: Suspend and reconcile regressions/drift, returning to a currently eligible policy within finite registered rollback bounds.
- **O4**: Qualify new native model/harness combinations and allow a simpler qualified P1 winner to replace an entire pipeline.
- **O5**: Preserve fixed-policy execution, user pins and inspectable local receipts when learning is disabled, unavailable or unsuccessful.

## Functional Requirements

Every named check below is prospective. Each must retain the stated negative input alongside a valid positive case, reach the actual decision branch and observe the policy pointer, admission pin, effect/operation record or typed refusal. A missing event alone is insufficient. Synthetic observations remain labelled synthetic.

### FR-1 — Immutable bounded data proposals (v2 §§4.1, 12.1–12.3)

- **AC-1.1** [I20/I22, AT-30] When proposing a policy, the system shall create an immutable canonical `PolicyVersion` with exact parent/content identity, eligible cohort, action family, evidence and rollback references; it shall verify algorithm-qualified content digests against retained bytes and reject mutation of a referenced revision. Prospective `TestPolicyProposalIsImmutable` retains changed content under the same identity and a digest copied onto different bytes.
- **AC-1.2** [I03/I04/I22, AT-30] When validating a candidate, the system shall allow only the explicitly approved subset of routing preferences among already eligible routes, bounded prompt templates, context selection strategies, review sequencing and decomposition settings within the fixed portfolio. It shall reject unknown fields, arbitrary executable/tool commands and changes to grants, funding, destinations, security ceilings, required context, protected acceptance/evaluators or promotion/rollback rules. Prospective `TestPolicyAllowedFieldsCannotWidenAuthority` retains a faster challenger with weakened checks, a hidden paid auxiliary and an instruction to run a new command. The exact closed field schema belongs to design investigation; open maps in the current record are not an allowlist.

### FR-2 — Exact protected cohort evidence (v2 §§7.1, 9, 12.2–13.3)

- **AC-2.1** [I07/I09/I14/I20, AT-23/AT-28/AT-29] When evaluating promotion or rollback eligibility, the system shall require a complete comparable evidence manifest binding source/task/dependency/candidate revisions, independent acceptance/check/evaluator definitions, context strategy/manifests, route/configuration/model identities, actual trust/enforcement, authority/funding scope, experiment/assignment versions, cohort and observation window. Only preregistered declared comparability may bridge a differing input; unknown mandatory identity blocks reuse. Prospective `TestPromotionRequiresExactComparableManifest` retains a changed evaluator, stale dependency, changed trust with the same label and a mismatched budget.
- **AC-2.2** [I07/I09/I20/I22, AT-29/AT-30] When checking a challenger, the system shall require preregistered population/unit, metric and useful-gain threshold, uncontaminated holdout, stated uncertainty/sample-adequacy method and stopping rule, all-started outcomes with missingness/censoring/delayed corrections, unchanged protected guards and full lifecycle costs. Default quality permits no registered regression: the registered one-sided quality bound must meet its floor and the target gain must meet its registered criterion under the same budget. A different non-safety quality margin requires explicit prior approval; no scalar score can buy permission or hide a guard failure. Prospective `TestProtectedPromotionEvidenceGate` retains a dev-only win, leaked holdout, absent overlap, underpowered result, favorable repeated peeking, dropped failure, human rescue omitted from cost and a quality-bound failure.
- **AC-2.3** [I07/I09/I20, AT-29/AT-31] If evidence is sparse, contradictory, materially corrected or invalidated, then the system shall retain historical conclusions under their original identities, refuse promotion reuse and record rejected/inconclusive/blocked reasons; it shall require a fresh eligible evaluation rather than relabeling missing data as a pass. Prospective `TestDelayedCorrectionInvalidatesPromotion` retains an initially accepted outcome followed by an attributable regression and a superseded qualification revision.

### FR-3 — Current qualification and separate authority (v2 §§7–8, 12.3)

- **AC-3.1** [I01/I02/I04/I14–I16, G02/G05, AT-30/AT-32] Before promotion, canary admission or rollback selection, the system shall resolve the exact native harness/surface, executable/adapter/configuration, model alias and resolved snapshot where available, host/platform, effort, tools/session behavior, entitlement/paid-continuation prevention and trust/security evidence at its current revision/expiry. An ambiguous or mutable unresolved identity shall not inherit another route's qualification; changed identity requires applicable requalification and re-admission. Prospective `TestPromotionUsesCurrentQualifiedRoute` retains expired evidence, sign-in without entitlement proof, an ambiguous alias and a formerly qualified rollback route that drifted.
- **AC-3.2** [I03/I04/I20/I22, AT-12/AT-30] When a proposal passes its evidence gate, the system shall present the exact evaluated proposal for approval unless a valid standing promotion grant explicitly covers its cohort, maximum policy change and registered rollback rule. Both grant paths shall bind issuer, applicable repository/host/environment/destination, exact policy or bounded policy rule, resource limits, expiry, revocation and permitted repetitions; default automatic activation is off. Proposal generation, model output, repository content, retrieved history and recorded past approval shall not mint or extend authority. Prospective `TestProposalCannotAuthorizeActivation` retains a forged approval in source text, expired/revoked scope, a grant for another cohort and an existing valid narrowly scoped standing grant.
- **AC-3.3** [I04/I15/I19/I21, G05, AT-03/AT-04/AT-13] If a proposed route consumes a different funding path, exceeds included allowance or needs unqualified auxiliary work, then the system shall block that effect and preserve the finite envelope; it shall not buy credits, cycle identities/accounts, extract native secrets or silently choose paid/API fallback. Prospective `TestPromotionCannotManufactureCapacity` retains an exhausted subscription and a proposal to retry under another identity or paid service.

### FR-4 — Staged activation and immutable episode pins (v2 §§4–6, 9.3, 12.3)

- **AC-4.1** [I20/I21/I23, AT-31] When activation is authorized, the system shall stage the immutable candidate and registered finite canary before atomically changing the cohort's active policy pointer and activation revision through the canonical ledger. Compare-and-set against the expected incumbent/cohort revision shall reject stale concurrent promotion/rollback; retry/reconnect with the same operation identity shall return its recorded result without repeating an effect. Prospective `TestActivationAtomicAndIdempotent` retains two competing expected-incumbent operations and crashes immediately before/after commit.
- **AC-4.2** [I04/I20/I23, AT-31] When a cohort policy/alias resolution changes, the system shall atomically bind the selected policy content/version, alias-to-resolved native identity, effective execution-policy revision and affected context epoch, and invalidate or explicitly quarantine affected pending preparations/confirmations and undispatched contexts. It shall not authorize old prepared bytes under new policy facts. If a compatible atomic boundary is unavailable, then it shall block activation. Prospective `TestActivationInvalidatesPreparedContext` retains a pre-change preparation confirmed after activation, an alias drift between prepare/start and a partial-write fault.
- **AC-4.3** [I06/I12/I18/I20, AT-31/AT-32] While an admitted episode is running or recoverable under its existing assignment, the system shall preserve its original policy, contract, context, evaluator, route/configuration and effect pins through retries, repairs and reconnect; only a fresh admission boundary may select a new policy. A safety/drift suspension may stop affected work and require reconciliation but shall never hot-swap its pins or executing code. Prospective `TestRunningEpisodePinsSurvivePromotion` retains an active repair/reconnect across activation and proves a subsequent freshly admitted episode uses the new revision.

### FR-5 — Canary guardrails and bounded rollback (v2 §§8, 12.3–13.3)

- **AC-5.1** [I07/I20/I21/I22, AT-30/AT-31] While a canary is active, the system shall enforce its preregistered eligible cohort, allocation/count/time/allowance limits, observation window, protected guardrails and regression rule. Any hard invariant breach shall immediately veto further affected assignments regardless of aggregate performance; a registered regression threshold shall trigger the registered rollback path. Completion of a finite canary shall require a new deterministic decision before widening allocation. Prospective `TestCanaryHardGuardVeto` retains a faster challenger with one authority violation, an ordinary registered regression and a count/time limit reached with pending observations.
- **AC-5.2** [I02/I04/I12/I14/I20/I21, AT-31/AT-32] When rollback is triggered, the system shall suspend affected future admissions, retain a durable reason linked to the trigger/evidence and choose only a rollback target currently qualified for the same protected cohort and within fresh applicable authority. A previous last-known-safe policy is not permanently qualified. If no target meets qualification, protected comparability or grant requirements, then rollback shall remain blocked with an actionable reason rather than dispatching an unsafe fallback. Prospective `TestRollbackRequiresCurrentSafeAuthority` retains a revoked rollback grant, expired incumbent evidence and a target with incompatible protected context/check inputs.
- **AC-5.3** [I06/I12/I18/I21/I24, AT-09/AT-31] If rollback encounters outstanding or uncertain effects, then the system shall reconcile ownership/effect outcome before retry, reassignment or resource reuse; it shall preserve active pins and never replay native tools/prompts merely by replaying an event. Within the finite registered rollback attempts/deadline it shall record rolled-back, failed or blocked/uncertain disposition and actual pointer revision; exhaustion requires explicit resolution. Prospective `TestRollbackReconcilesUncertainEffects` retains response loss after a committed pointer change, a still-running writer, failed reconciliation and a crash during rollback.

### FR-6 — New model and harness lifecycle (v2 §§7, 12.4, 13.3)

- **AC-6.1** [I01/I02/I03/I14/I19/I22, AT-32] When optional metadata discovery finds a model/harness, the system shall keep it ineligible until explicit native installation/update outside learning, documented capability inspection, offline compatibility, separately authorized live fidelity/billing/security qualification, development calibration, bounded held-out evaluation, canary and scoped promotion have produced versioned evidence. A stage may remain blocked with its reason; metadata, model naming or external claims shall not skip stages or invoke an installer/provider. Prospective `TestMetadataCannotQualifyModel` retains a catalogue entry absent locally, unsupported effort/subagents and fixture-only success presented as live qualification.
- **AC-6.2** [I01/I04/I14/I16/I20, AT-32] When dispatch/reconnect detects relevant native binary, adapter, model resolution, configuration, startup, tools/session, entitlement or security drift, the system shall suspend affected admissions and require appropriate requalification while reconciling active pinned work; unrelated qualified routes may remain available within their grants. Unknown mutable provider identity shall remain visible and use a registered expiry/drift rule. Prospective `TestModelDriftSuspendsAffectedAdmissions` retains native auto-update, silently retargeted model alias, changed paid-continuation behavior and an unaffected independently qualified route; no API fallback is permitted.

### FR-7 — Whole-pipeline replacement and honest claims (v2 §§10.2, 13.1–13.3)

- **AC-7.1** [I07/I09/I20/I22, AT-29/AT-30/AT-34, G14] When a new qualified P1 challenger is compared with an incumbent pipeline, the system shall evaluate complete useful accepted outcomes against the whole pipeline and strongest simpler eligible baseline with matched source/contracts/tools/environment/budget/intervention rules and disclosed unavoidable differences. Review, investigation, retries, verification, human effort, missing outcomes and delayed regressions shall remain visible. Only the registered protected gate and scoped authority may replace the pipeline. Prospective `TestP1MayReplaceWholePipeline` retains a useful qualifying P1 winner, a drop-in-only comparison and a baseline stopped before review.
- **AC-7.2** [I07/I09/I14, AT-29–AT-34, G14] If matched authorized live evidence does not establish a useful scoped improvement, then the system shall retain useful fixed execution and label adaptive promotion experimental or blocked; synthetic rejection/rollback demonstrations and routine delivery observations shall not become productivity claims. Prospective `TestAdaptiveClaimsRequireLiveEvidence` retains successful synthetic faults with no live cohort and a live inconclusive result, alongside a separately reviewed matched result scoped to its exact versions.

### FR-8 — User controls, disabled learning and receipts (v2 §§5.3, 8.4, 12.3, 15, 17.2)

- **AC-8.1** [I02/I13/I20/I25, AT-27/AT-33] When a user disables learning, revokes exploration consent, pins a currently qualified policy or loses the optional learner/store/index, the system shall preserve authorized fixed-policy delivery and essential operational receipts without hidden discovery, estimator updates, backfill, experiments or automatic promotions. A previously selected fixed policy may remain pinned if current admission still permits it; unsupported pins shall produce an honest blocker. Active experimental effects require bounded cancellation/reconciliation under the registered rules. Prospective `TestLearningDisabledPreservesFixedDelivery` retains an absent/corrupt learner, zero budget and revoked consent during a canary, using call sentinels that detect hidden native/model/network work.
- **AC-8.2** [I09/I20/I23/I25, AT-27/AT-28/AT-31/AT-35] When proposing, rejecting, authorizing, activating, suspending or rolling back a policy, the system shall retain a linked local receipt with exact policy/cohort/evidence/authority revisions, decision inputs/reasons, old/new pointers, pins, stage/operation identity, resource observations and unresolved uncertainty. Users shall inspect, export and pause/stop through approved core interfaces within repository scope; derived views shall not become a second task store or grant surface. Optional learning retention/erasure shall use approved dependency roots and disclose remaining copies. Prospective `TestPolicyDecisionReceiptRoundTrip` retains an unknown measurement, rejected decision, blocked rollback and cross-repository unauthorized read.

## Non-Functional Requirements

- **NFR-1** [I13/I21/I25, AT-33] Default exploration, discovery, canary and automatic promotion budgets shall be zero attempts and zero allowance/monetary authority, with no background schedule. Offline gate/contract fixtures shall execute zero native/model/provider/network calls (`TestOfflinePromotionGateHasNoEffects`, retaining a sentinel that would fail on invocation). An approved standing grant may enable only its bounded scope.
- **NFR-2** [I20/I21/I23, v2 §§4–5] The first offline implementation shall bound one evaluation request to 1 MiB of policy/manifest metadata, 128 evidence references, 16 candidate versions, one cohort and one proposed transition; overflow shall return a typed refusal before mutation. Referenced artifacts remain separately bounded by their owning contracts; ingestion streams or rejects oversized histories rather than loading them without limit. `TestPromotionInputBounds` shall retain limit-plus-one cases, malformed/nonfinite metrics, duplicate/unknown keys and cyclic parent/rollback links. These are delegated conservative starting caps, not claims about existing API limits; design must reconcile tighter shared limits.
- **NFR-3** [I10/I21/I24, AT-26/AT-31] Every enabled canary/rollback shall have pre-authorized finite count, wall-time, allowance and attempt caps, a non-empty observation window and a registered uncertainty/stopping rule before its first assignment. Foreground verification/repair reserves cannot be borrowed, and all auxiliary/retry cost counts. `TestCanaryRollbackBudgetExhaustion` shall retain each zero/exhausted cap and pressure with a live owner; cancellation/reservations shall not be called provider hard caps. No universal sample minimum substitutes for registered power/adequacy.
- **NFR-4** [I12/I20/I23, AT-31, G16 boundary] Canonical transition faults shall produce either the entire prior committed state or the entire new state; reconnect/replay shall not create another activation or native effect. `TestPolicyTransitionCrashMatrix` shall cover before-commit, after-commit-before-response and recovery at each logical transition. New storage is additive, older event decoding preserved and unknown newer schemas refused without writes; exact migrations/compatibility work require reviewed design and appropriate ADRs.
- **NFR-5** [I03/I09/I25, v2 §§5.3, 8.4, 17.2] Default receipts/features shall exclude raw source/task text, native secrets and cross-project identifiers; visibility follows explicit repository/cohort consent, never global pooling by a label. `TestPolicyEvidencePrivacyScope` shall retain an unauthorized cohort lookup and secret-bearing synthetic proposal. Existing approved export/erasure and backup limitations remain explicit; no indefinite optional learning retention is introduced here.

## Open Questions

These are bounded design investigations owned by the coordinating technical lead, with evaluation and native-integration review for their areas; they are not founder decisions or permissions. Conservative defaults apply until an exact approved design supersedes them. This spec remains unrefined and requires fresh independent refinement.

- **OQ-1 — Merged dependency interfaces** (blocks dependent implementation): which exact approved outcome/experiment/consent/retention and service-binding revisions are available? Options: bind a merged contract, adapt after reviewed change or retain a blocked seam. Default: offline synthetic contracts only until actual merged interfaces are inspected; do not implement pending requirements as guessed APIs.
- **OQ-2 — Live evidence and grant scope** (blocks activation/live claims): which exact native cohort, trust/funding protections, expiry rules and scoped authority can be substantiated? Options: qualify a bounded subset or keep it blocked/experimental. Default: no live calls/activation, current qualified fixed P1 only where admission permits it. A standing grant is allowed by v2 but never inferred from this task or a proposal.
- **OQ-3 — First field subset and registered protocol** (blocks runtime policy schema/canary design): select the smallest useful closed subset and preregister cohort, quality/gain bounds, uncertainty method, observation window, allocation and rollback caps before results. Options: one bounded prompt/context change or qualified P1 pipeline replacement; broader combinatorial search is deferred. Default: one cohort/one change, NFR-2 metadata caps, zero enabled canary/exploration until a finite explicit protocol is approved; no weakening of protected safety/authority.
- **OQ-4 — Atomic composition and safe suspension** (blocks activation implementation): choose the exact canonical transaction boundary joining policy pointer, alias/policy revision, context epoch and pending preparation invalidation, and define how affected active effects reconcile. Options: an additive canonical projection or a reviewed existing-owner extension. Default: refuse activation if full atomicity/current evidence cannot be proven; never patch live pins. Persistence/ownership/billing changes require architecture review and ADR as applicable.
