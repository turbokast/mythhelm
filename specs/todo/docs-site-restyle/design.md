### 2. Scope determination

Single spec, ~11 tasks, three domains (docs, harness, release) plus a product decision entry filed by approval. Why not an epic: the work streams (layout and content, harness checks, workflow wiring) deliver nothing usable shipped alone — a layout without its checks can claim more than ships (I14, G10), checks without the layout have no conforming site to check, and wiring without either gates nothing. The coupling is through five small contracts shipped by Task 1 (brand token table, layout marker, `status.yml` schema, examples-list schema, search-index shape and `manifest.json` chapter schema); after Task 1 the content tasks and the harness checks proceed in parallel against those contracts. Splitting into sub-specs would duplicate the contracts and drift them. Above the 10-task guideline but below the 14-task epic threshold in `/spec-scope`; `design.md` records the reason here as that skill requires.

### 3. Design by area

#### 3.1 Brand tokens, layouts and fonts (FR-1, v2 §15.1 by decision D-97, G10)

- `docs/assets/brand/README.md` gains Paper `#f6f4ee`, Amber (dark) `#f0c27b` and Amber (light) `#8a5a00` with the rule "amber means needs you and nothing else" (AC-1.2, OQ-11). The site stylesheet holds every colour as a CSS custom property whose name and hex equal a table row; `transparent` and `currentColor` are the only non-token literals and derived tints are forbidden, so muted text on Paper is Ink (AC-1.2). Task 1 ships the table and the stylesheet together so the parity check of Task 8 has both sides from the start.
- One layout file keeps the name `default` (AC-1.1, decision D10): `docs/_layouts/default.html` branches on the page — the landing page (`docs/index.md`) renders the Night surface and every other page the Paper surface — so the five places that name the layout (the four front-matter pages and the mirror injection step in `.github/workflows/docs.yml`) need no rename. `docs/_config.yml` gains a `defaults:` entry assigning `default` to every page explicitly. Every built page carries the exact marker `<!-- mythhelm-layout:v1 -->` in its `<head>`, which the Task 8 check asserts on every published page (AC-1.1). `theme: minima` is removed from `docs/_config.yml` and no built page links minima's `assets/main.css`.
- Fonts: Archivo Expanded ExtraBold for the wordmark and JetBrains Mono with a system monospace fallback for code and labels, self-hosted as WOFF2 subsets from the site origin with the OFL notice beside them, the source release, SHA-256, subsetting command and any Reserved Font Name recorded beside the files, and the brand README's non-redistribution sentence updated in the same change (AC-1.4, OQ-3). No third-party font load (AC-1.5, NFR-1).

#### 3.4 Client-side search (FR-4)

- The Jekyll build emits a static JSON index of every published page (title, group, headings with anchors, body text) with no runtime service: source template `docs/search.json` (YAML front matter `layout: null`, so Jekyll runs Liquid without applying the site layout or the `defaults:` assignment) built to `_site/search.json` and fetched from the layout-emitted `{{ '/search.json' | relative_url }}` URL (`/mythhelm/search.json` under `baseurl: /mythhelm` in `docs/_config.yml:8`) only on first search use so it never counts toward landing weight (AC-4.1, NFR-3, I13). The design bounds the index at 300 KB uncompressed (NFR-5): when it would exceed that, body text is truncated per page, largest first, never titles or headings; `docs/spec/master-spec.md` alone is 217,947 bytes (`wc -c docs/spec/master-spec.md` in the built tree is measured by Task 5, not assumed). A truncated page is marked as truncated in results so a body-text miss there is not presented as "no match" (AC-4.2).
- Ranking is title and heading matches first, each result linking to its anchor; a query matching nothing says so (AC-4.2). The control is keyboard-reachable (documented shortcut and Tab), announces result counts to assistive technology, and works offline once page and index are loaded (AC-4.3). Without JavaScript the control is hidden and every page stays readable and navigable (AC-4.4). Task 8's coverage check fails when the index lacks a sidebar-listed or G10 page (AC-4.5). If a Liquid-generated index cannot be built under `actions/jekyll-build-pages` (Pages allows no custom plugins; `docs/_config.yml:6` is `plugins: []`), Task 5 stops and reports to the maintainer and the card's Starlight/mdBook revisit applies (OQ-5) — it does not substitute a build system.

#### 3.5 State labels and declared notes (FR-5, I09)

- One markup convention — the Liquid include `{% include state.html state="<reported|estimated|unknown>" %}` (file `docs/_includes/state.html`, single argument `state`) — renders `reported`, `estimated` and `unknown` consistently on both surfaces, `unknown` with a dotted underline, each state distinguishable without colour (AC-5.1). `docs/user-guide.md` prose that names a state as a data label (the budget-section definitions and the "unknown rather than zero" sentences) uses the convention; ordinary English, output lines, field paths and other enums stay verbatim (AC-5.2, N2: prose is not rewritten, only marked up; in `docs/limitations.md` only state words naming a data label, never headings or Windows lines). An empty or unrecognised state renders `unknown`, never blank or zero (AC-5.2, I09).
- A neutral "declared, not verified" note style (no amber, OQ-6) marks statements MYTHHELM does not verify, applied to the user guide's declared-billing and entitlement statements (AC-5.4, I14).

#### 3.6 Tested examples (FR-6, G10, I14, AT-46)

- A checked-in examples list (`docs/_data/examples.yml`: entries `{anchor, command, expect_exit}`) is the only source of the "tested in CI" marker. An `anchor` identifies exactly one fenced block as `<page>#<heading-slug>[<n>]`: `page` is the docs-relative source path (e.g. `docs/user-guide.md`), `heading-slug` is the GitHub slug of the nearest preceding second-level heading, and `n` is the 1-based ordinal of the fenced block under that heading. An entry for an output block also carries `output_anchor` in the same format, naming the block that shows the command's output. Drift (AC-6.3) compares, after CRLF-to-LF conversion and trailing-whitespace trimming on each line (the fixed normalisation `docs-output-v1`; no other rewriting), the block's text lines exactly against the lines the entry's command is documented to show; for an output entry the Task 10 examples job runs the command, applies `docs-output-v1` to its stdout and compares it line-by-line with the `output_anchor` block (AC-6.4). Any difference fails, and an anchor resolving to zero or to more than one block fails. a block with no entry renders without it and the existing `<!-- Output of: … -->` comments earn nothing by themselves (AC-6.1). The quickstart `go run ./cmd/mythhelm demo` is the first entry, run non-interactively with `GOPROXY=off` after `go mod download` (AC-6.2). Each entry records its expected exit code so a refusal block is listed with that code or never marked (AC-6.2). A block showing command output is marked only when the job diffs normalised output against the block (AC-6.4).
- The examples job runs every listed command as written in the site-build job of §3.8, needs no agent credentials and no paid service, and runs on fork pull requests; a structural check fails when `.github/workflows/ci.yml` (which hosts the `site-build` job) or `.github/workflows/docs.yml` references `secrets.` for these jobs or uses `pull_request_target` (AC-6.5, AT-46). The fork run itself is a recorded maintainer inspection, not an automated check (AC-6.5).

#### 3.7 Responsive and accessible layout, browser driver (FR-7)

- Every published page has document scroll width no greater than the viewport at 390px and 1280px, asserted per rendered page including `user-guide.html`, and no element's box passes the viewport outside an `overflow-x: auto|scroll` container, so `overflow-x: clip` on `html` or `body` cannot hide an overflow (AC-7.1). Interactive targets are at least 44×44px at 390px; the same pass asserts the AC-2.1 first-viewport position and NFR-3 weight on the landing page (AC-7.2).
- Contrast: body text and links meet 4.5:1 and large text and UI parts 3:1, computed from the rendered pages, not a hand-kept pair list; Star light `#00829d` on Paper (4.08:1) is used only for large text and UI parts, links and small text on Paper in Ink with a Star underline or marker (AC-7.3, OQ-4).
- Demo images fit the column with the caption below; every recording carries a text alternative naming what it shows and that it is scripted. The user guide's three autoplaying GIFs (`docs/user-guide.md:39-46`) and the landing GIFs are served as their Task 2 posters: the markup shows the poster `<img>` with a labelled start control, and `docs/assets/site.js` (Task 4) swaps in the GIF (or the AC-2.2 `<video>` for the hero) only on request; Task 6 applies that markup in `docs/user-guide.md`. With `prefers-reduced-motion` the swap never happens unprompted and the poster stands in (AC-7.4, AC-7.5); the palettes ignore the visitor's colour-scheme preference. Task 9's driver asserts no GIF is fetched or animating before the start control is used.
- The measurement driver is a pinned headless-Chrome Node script in exactly one carved-out directory, `scripts/ci/browser/`, invoked exactly as `node scripts/ci/browser/check_layout.mjs _site` (site directory argument), allowed by an explicit carve-out in `.claude/rules/harness-scripts.md` for that directory and nowhere else under `scripts/**` (AC-7.6, OQ-5). Its tests run only in the `ci.yml` site-build job after `npm ci` and never skip when Chrome is missing; every other new check is Bash or Python standard library gated by CI OK's harness job (AC-7.6). Supply-chain terms are NFR-6: committed lockfile and `npm ci`, `actions/setup-node` pinned by full SHA with no dependency cache in the deploying workflow, an `npm` entry in `.github/dependabot.yml` with the 7-day cooldown, a stated browser source (the runner's preinstalled Chrome with its version recorded, or a checksum-verified download), new rows in `docs/automation.md`, and a licence check of every package in the resolved tree against the dependency-review allow-list before the driver lands — if any licence is off the list the task stops and reports, never widening the list itself (NFR-6).

#### 3.8 Checks and workflow wiring (release, harness)

- Harness checks (Task 8, Python/Bash, fixtures under `scripts/ci/tests/fixtures/` for non-Jekyll fixtures and a separate check build for Jekyll-rendered ones, never under `docs/` and never deployed, NFR-4): token parity and stylesheet literals (AC-1.2), amber `var()` ban (AC-1.3), off-origin resources and the script allow-list `docs/_data/site-scripts.yml` (`{src, purpose}` with `purpose` in `search`, `sidebar`, `player`; created by Task 1, consumed here) including recorded browser requests (AC-1.5), panel phrase anchoring, column and tracker binding and cell-label agreement (AC-2.3, AC-2.4), footer targets (AC-2.5), state-word wrapping and source-markup validity with the three states present at least once (AC-5.3), layout-marker coverage on every published page (AC-1.1), hero chapter offsets strictly increasing and within the rendered video's duration read from the file (AC-2.2), marker-without-entry, empty list and first-entry-is-quickstart (AC-6.1), entry/block drift both ways (AC-6.3), the marker-without-`output_anchor` guard (AC-6.4; the executing diff is Task 10's), search-index coverage (AC-4.5) and index size (NFR-5). Each check ships a rejecting fixture as its AC requires; a check that can pass on zero matches is a defect (see `knowledge/spec-authoring.md` patterns).
- Workflow (Task 10, release): the site builds once; the artifact is uploaded immediately after the build and "Assert mirrors rendered" and before any browser, npm or example step; the deployed site is that artifact (or the two builds' tree digests are compared), fixtures build to a different `destination:` and a check proves the deployed tree contains no fixture marker (AC-6.2). A site-build job with id `site-build` and name `Site build` in `.github/workflows/ci.yml` is added to the `needs:` list of `CI OK` so every new check blocks merges through the already-required CI OK with no ruleset change and `.claude/data/required-checks.json` unchanged (AC-6.2, OQ-10). No existing `.github/workflows/docs.yml` assertion is removed or weakened and the mirror injection never runs before a passing mirror-freshness check (AC-2.5, AC-6.2). `docs/automation.md` gains rows for the new checks and the npm driver (NFR-6, `.claude/rules/github-workflows.md`: every new action pinned to a full SHA).
- Sequencing: Task 1 ships the contracts; content tasks wire each check in the same task that makes its content conform, or the check lands disabled-by-absence (no fixture, no gate) until its content task merges, so no pull request turns red before its content is ready (requirements Dependencies). The harness carve-out (Task 9) precedes the browser driver; the landing page depends on the hero render (Task 2) and the status data (Task 3).
