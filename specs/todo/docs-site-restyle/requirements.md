## Docs Site That Shows the Product — Requirements

> Refined. All twelve decisions are confirmed per item, including the ones the architect review reopened (see Decisions). Run /spec docs-site-restyle next.

> Restyle the Jekyll site on GitHub Pages in the brand: a Night landing page that leads with the hero recording and the quickstart, Paper docs pages with a grouped sidebar, an on-this-page list and client-side search, consistent reported / estimated / unknown labels, code examples marked "tested in CI" only when CI runs them, and no horizontal overflow at 390px. A slice of the public release gate G10 and the design direction D-97. Normative source: mythhelm-synthesis/MYTHHELM_Master_Spec_v2.md, version 2.0 (via docs/spec/README.md); § numbers, I-IDs, G-IDs and AT-IDs refer to it.

### Objectives

- **O1**: A person landing on the site sees what MYTHHELM does and the quickstart without scrolling: at 1280x800 and 390x844 the top edge of the quickstart block is inside the first viewport (D-97, G10).
- **O2**: A reader of any docs page finds their way by grouped navigation, an on-this-page list and search, on a phone as well as a desktop (D-97).
- **O3**: Nothing on the site's checked surfaces claims more than ships (the headline is the maintainer's own statement, qualified by the pill and the panel link, OQ-1): the status panel, the state labels and the "tested in CI" marker are each backed by a source a check reads (I09, I14, G10).
- **O4**: The site is on brand and legible in both palettes without a build system beyond Jekyll (D-97).

## Functional Requirements

Acceptance criteria use EARS. Tags in brackets name the invariants, gates and sections each one serves.

### FR-1 — Brand layout and tokens (D-97, G10)

- **AC-1.1** [D-97, v2 §15.1, G10 (v2 §18.3)] When a published page is built, the site shall serve a layout that carries the brand tokens (Night, Frost, Ink, Star dark and light, Mist, Paper, the two amber values) as CSS custom properties and the M crest mark in the header: the landing page on the Night surface and every other page on the Paper surface. The layout keeps the name `default` (`layout: default` in the four pages' front matter and in the mirror injection step of the build job; front-matter-less pages receive a layout through the Pages defaults, which the design confirms with a build, so a `defaults:` entry in `docs/_config.yml` assigns the docs layout to every page explicitly, and a check on the built site fails when a published page lacks the layout's marker, with a fixture page that lacks it) or the same change updates those five places; `theme: minima` and its `assets/main.css` are either removed or no longer determine any visible style, and the choice is recorded in the design.
- **AC-1.2** [D-97, v2 §15.1, G10 (v2 §18.3)] Every colour literal in the site's stylesheet (hex, `rgb()`, `hsl()` or named colour) shall be the value of a custom property whose name and hex appear in the brand README's colour table (`docs/assets/brand/README.md`), and a check shall fail when a literal is outside the table or a table row differs from the stylesheet; the check ships with a stylesheet fixture holding an unlisted hex and a fixture whose table row differs from the stylesheet's property, each of which it must reject. `transparent` and `currentColor` are allowed; derived colours (alpha channels, `color-mix()`, `opacity` used to tint text) are not, so muted text on Paper uses Ink and a new token is a brand change for the maintainer. The brand README's colour table gains these rows (OQ-11): Paper `#f6f4ee` (docs surface), Amber (dark) `#f0c27b` and Amber (light) `#8a5a00`, each with the rule "amber means needs you and nothing else", next to the existing Night, Frost, Ink, Star and Mist rows.
- **AC-1.3** [D-97, v2 §15.1, G10 (v2 §18.3)] Star shall be the only accent colour on both surfaces, and the site has no "needs you" element, so no rule outside the token declarations shall reference an amber token (OQ-6: the "declared, not verified" note is neutral); the check fails on any such `var()` reference and ships with a fixture rule that does so, which it must reject. The landing page's attention cell uses no amber chip.
- **AC-1.4** [D-97, v2 §15.1, G10 (v2 §18.3)] The code and label face shall be JetBrains Mono with a system monospace fallback, the body face a readable system or secondary stack, and the wordmark Archivo Expanded ExtraBold. Both faces are self-hosted as WOFF2 subsets from the site's own origin with the OFL notice shipped beside them (OQ-3); no font is loaded from a third party. The font files' source release, SHA-256, subsetting command and any Reserved Font Name are recorded beside them, and `docs/assets/brand/README.md`'s sentence that the fonts are not redistributed is updated in the same change.
- **AC-1.5** [D-97, v2 §15.1, G10 (v2 §18.3), I14 (v2 §2)] If a page of the built site requests a resource from an origin other than the site's own, then a check shall fail: it fails on any such reference in the HTML and CSS (`src`, `srcset`, `poster`, `<source>`, `<iframe>`, `<link rel=preload|icon|stylesheet>`, CSS `url()` and `@import`) and on any network request recorded by the headless-browser pass at both widths; links the reader follows (GitHub, issues) are not loaded resources and do not count. The check ships with a fixture page that loads a script from another origin and a fixture stylesheet with an `@import` of another origin, each of which it must reject. Analytics are checked at source: every script file on the built site must be listed in the checked-in allow-list `docs/_data/site-scripts.yml` (a YAML list of `{src, purpose}` entries, `src` the site-relative built path such as `assets/search.js`, `purpose` one of `search`, `sidebar` or `player`), so a self-hosted analytics script or a dependency that is not listed fails the check, with a fixture that adds one.

### FR-2 — Night landing page with the hero recording (D-97, G10)

- **AC-2.1** [D-97, v2 §15.1, G10 (v2 §18.3)] The landing page shall show, in this order: the nav (crest mark, search, "pre-alpha" pill), the headline "Run the agents you already trust. Know what they actually did." (OQ-1), the `go run ./cmd/mythhelm demo` quickstart, the hero recording, four "why not just tmux" cells each paired with the peer-user need it answers, the works / in progress / not yet panel, and the footer; at 1280px and at 390px the order is the same and the top edge of the quickstart block lies within the first 800px and 844px of height respectively. The pill stays in the nav, and exactly one one-line link to the status panel sits under the headline (OQ-1); a check fails when the landing page lacks it.
- **AC-2.2** [D-97, v2 §15.1, G10 (v2 §18.3), I14 (v2 §2)] The hero recording shall be the real recording of `docs/demos/hero.tape`, shall carry chapter controls (title, run, kill, recover, review) that seek to the matching moment, shall not autoplay, and shall have a poster. The recording is rendered from the same tape as `hero.webm` with an MP4 fallback and played in an HTML5 `<video>` whose chapter buttons take their offsets from `docs/demos/manifest.json` (OQ-2); a check fails when the offsets are not strictly increasing or exceed the video's duration read from the rendered file (not from a manifest field), and ships with a fixture manifest that does either. The transcript-freshness job is unchanged; it covers the tape's commands, not the video bytes.
- **AC-2.3** [I14 (v2 §2)] The works / in progress / not yet panel shall be generated from a data file (`docs/_data/status.yml`) whose items each name a section of `docs/limitations.md` and quote a phrase from it, and a check shall fail when a quoted phrase is absent from the named section's text (anchored to the region under that heading, not the whole file); the check ships with a fixture whose quoted phrase was removed from its section, which it must reject. The panel has three columns (OQ-9) whose data values are exactly `works`, `in-progress` and `not-yet` (the rendered headings may read "Works / In progress / Not yet", but the `column` field, the renderer and the check use the hyphenated values verbatim): `works` is fed by "Supported today" and the limits sections, `in-progress` by the "Not supported yet" items that name an open issue or a spec in flight, each stating its tracker, and `not-yet` by the other "Not supported yet" items; a capability that is neither shipped nor in flight in that sense is labelled `not-yet`. The check also fails when an item's column does not match its source section (`works` only from "Supported today", the limits sections only as caveats shown on a `works` item, `in-progress` and `not-yet` only from "Not supported yet"), when the displayed item text is not the quoted phrase, and when an `in-progress` item's tracker (issue or spec) is not inside the quoted region, so `docs/limitations.md` stays the single source and the check needs no network call; each of these ships with a rejecting fixture.
- **AC-2.4** [I14 (v2 §2), G10 (v2 §18.3)] Each "why not just tmux" cell shall name the capability it rests on and link its evidence (a `docs/limitations.md` section, a user-guide section or a qualifying test named in `docs/demos/manifest.json`), and a cell whose capability is not shipped shall carry the label the panel gives that capability under AC-2.3 (`in-progress` or `not-yet`), never be stated as working. The four cells are attention (paired with approvals; MH-23 is `triaged` with no spec, so "not yet"), recovery (session recovery), readable evidence (readable verification) and honest budget (quota gauge) (OQ-1). Each cell names a `docs/_data/status.yml` item id; the check of AC-2.3 fails when a cell's label differs from its item's label or its item is missing, and a cell that rests on a working capability carries the quote of that capability's limit; each ships with a rejecting fixture. The headline's wording is the maintainer's statement and is not machine-checked; its qualification is the pill and the panel link.
- **AC-2.5** [G10 (v2 §18.3)] No existing assertion in `.github/workflows/docs.yml` (mirror freshness, manifest revisions, transcript freshness, qualifiers, "Assert mirrors rendered") shall be removed or weakened, and every published page shall show links to the licence, security policy, changelog, governance, limitations and contributing pages in a place visible without opening a control (the footer); `docs/_data/navigation.yml` adds the governance page, which is today reachable only through `docs/contributing.md`. The existing footer line "Rendered from commit ..." stays in both layouts, and a check fails when a footer link's target does not exist in the built site (fixture: a footer link to a missing page).
- **AC-2.6** [D-97, G10 (v2 §18.3)] The quickstart block on the landing page and in the user guide shall be the same command text, copyable, with the note that the first build needs the Go module cache populated (`README.md:46`).

### FR-3 — Paper docs layout (D-97)

- **AC-3.1** [D-97, v2 §15.1, G10 (v2 §18.3)] A docs page shall show a sidebar whose entries are grouped under Start, Use, Understand and Reference, with at most four top-level groups and the current page marked; the group of every page in `docs/_data/navigation.yml` is data in that file, not hard-coded in the layout. The user guide has one entry per group it spans, with deep links to its anchors under Start, Use and Understand, and is not split into pages (OQ-7). Every rendered page keeps rendering with the Paper layout and is covered by the checks; the maintained ones (release process, automation, decisions) are listed under Reference and the rest stay out of the sidebar (OQ-8).
- **AC-3.2** [D-97, v2 §15.1] A published page with two or more second-level headings shall show an on-this-page list of those headings, generated at build time, each linking to its anchor; a page with fewer than two second-level headings shows none.
- **AC-3.3** [D-97, v2 §15.1, AT-36 (v2 §18.2)] The prose column shall be bounded to at most 80 characters per line, and a long `pre` or `table` shall scroll inside its own container, never widen the page.
- **AC-3.4** [D-97, v2 §15.1, AT-36 (v2 §18.2)] Where the viewport is narrower than 1024px (the sidebar breakpoint), the sidebar shall collapse behind a labelled control that works with keyboard and touch and, without JavaScript, shall remain reachable as a plain link list.
- **AC-3.5** [D-97, v2 §15.1] The four mirrored root-guide pages shall render in the same layout with the same sidebar and on-this-page list.

### FR-4 — Client-side search (D-97)

- **AC-4.1** [D-97, I13 (v2 §2), G10 (v2 §18.3)] The build shall emit a static search index of every published page (title, group, headings with anchors, body text; `group` is the page's `docs/_data/navigation.yml` group when the page is listed there and the literal `none` for every other published page, which deliberately stays out of the sidebar), generated by Jekyll with no runtime service, and fetched only when the visitor first uses search from the URL the layout emits with the Jekyll `relative_url` filter (`{{ '/search.json' | relative_url }}`, i.e. `/mythhelm/search.json` under the configured `baseurl: /mythhelm`), so the index never counts toward the landing page's weight (NFR-3); the design bounds the index's size, for example by excluding the body text of the largest pages (`docs/spec/master-spec.md` alone is 217,947 bytes, `wc -c`). When the index would exceed NFR-5, body text is truncated per page, largest page first, never titles and headings, so unrelated growth (for example the changelog mirror) does not fail the build.
- **AC-4.2** [D-97, v2 §15.1] When a visitor types a query that matches a heading or body text, the search control shall list matching pages and sections ranked with title and heading matches first, each linking to its anchor; a query matching nothing shall say so. The guarantee covers the text the index holds: title and headings of every page are always indexed, and a page whose body text AC-4.1 truncated is marked as truncated in the results, so a body-text miss on such a page is not presented as "no match".
- **AC-4.3** [D-97, v2 §15.1, AT-36 (v2 §18.2)] The search control shall be reachable by keyboard (the `/` shortcut, which focuses search when the visitor is not typing in a field — v2 §15.1's `/` filtering — and by Tab; the shortcut is documented beside the control), announce result counts to assistive technology, and work offline once the page and index are loaded.
- **AC-4.4** [D-97, v2 §15.1, AT-36 (v2 §18.2)] While JavaScript is unavailable, the page shall hide the search control rather than show an inert one, and every published page shall remain readable and navigable.
- **AC-4.5** [D-97, G10 (v2 §18.3)] A check shall fail when the built index lacks a rendered page the sidebar lists or that is a G10 page, and shall be shown to pass on the built site and fail on a copy of it with one page removed from the index.

### FR-5 — State labels (I09)

- **AC-5.1** [I09 (v2 §2)] The site shall define one markup convention for the three data states `reported`, `estimated` and `unknown`, documented for authors, rendered with a consistent style on both surfaces: `unknown` with a dotted underline, and each state distinguishable without colour. User-declared data is covered by AC-5.4.
- **AC-5.2** [I09 (v2 §2)] Where the user guide's prose names a state as a data label MYTHHELM prints or records (the label definitions in its budget section, `grep -n "for exact\|estimated" docs/user-guide.md`, and the sentences saying a field is `unknown` rather than zero), the prose shall use the convention: a code span holding only a state word that names a data label MYTHHELM records becomes the markup (``grep -n '`\(reported\|estimated\|unknown\)`' docs/user-guide.md`` lists the candidates; the design names which are in scope). Ordinary English uses of the words ("unknown keys", "the reset is unknown"), output lines such as `remaining: unknown`, field paths and the values of other enums stay verbatim. If the markup is given an empty or unrecognised state, then the built page shall render `unknown`, never a blank and never zero; the check of AC-5.3 renders a fixture page doing so.
- **AC-5.3** [I09 (v2 §2)] A check shall fail when the state class wraps text other than one of the three state words (it ships with a fixture page that does so, which it must reject), and the three states shall each appear in at least one built page so the check cannot pass on zero matches. The check also fails on the source markup when its state argument is empty or not one of the three words (a typo such as `estimeted`, or an `observed` label), with a fixture for each; the render-time fallback to `unknown` of AC-5.2 is the last resort and both are asserted.
- **AC-5.4** [I14 (v2 §2)] A "declared, not verified" note style shall exist for statements MYTHHELM does not verify, and the user guide's declared-billing and entitlement statements shall use it (a markup change; the text is not rewritten). The style is a neutral border and label and uses no amber (OQ-6).

### FR-6 — Code examples marked and tested in CI (G10, I14)

- **AC-6.1** [I14 (v2 §2)] A fenced code block shall carry a "tested in CI" marker only when an entry in a checked-in examples list names it and the command that CI runs for it; a block with no entry shall render without the marker. The existing `<!-- Output of: ... -->` provenance comments in `docs/user-guide.md` (`grep -c "Output of" docs/user-guide.md`) stay and do not earn the marker by themselves. The marker is generated only from the examples list, and a built-site check fails on any marked block that has no matching entry (a fixture page marks a block by hand), on an empty list, and on a list whose first entry is not the quickstart.
- **AC-6.2** [I14 (v2 §2)] A CI job shall run every listed example command as written and fail when a command's actual exit code differs from its entry's expected exit code (0 unless the entry records another; the check ships with a fixture entry expecting 0 whose command exits non-zero) or when an entry names a block that no published page contains (the check ships with a fixture entry naming a missing block, which it must reject); the quickstart `go run ./cmd/mythhelm demo` shall be the first listed example, run non-interactively with no module downloads (after `go mod download`, with `GOPROXY=off`; "offline" in this criterion means the build, and the demo's own runtime claim of no network is covered by `TestDemoOfflineNoCredentials`, not asserted by the marker). The examples job and every other new check run in a site-build job added to the `needs:` list of `CI OK` in `.github/workflows/ci.yml` (OQ-10), so they block merges through the already-required `CI OK` with no ruleset change; `ci.yml` already triggers on `merge_group`. The mirror front-matter injection never runs before a passing mirror-freshness check. Each entry records the exit code the command is expected to return, so a block that shows a refusal (for example a `subscription-only` run, which exits non-zero) is either listed with that code or never marked; `GOPROXY=off` proves the build needs no network, not that the quickstart's prose claim about runtime network use holds, and the marker does not imply it. The site those checks ran on is the site deployed: the design either builds once and hands the artifact to `deploy`, or compares the digests of the two builds' trees; the artifact is uploaded immediately after the build and "Assert mirrors rendered" and before any browser, npm or example step; fixtures are built into a different `destination:`, and a check proves the deployed tree contains no fixture marker (red-first).
- **AC-6.3** [I14 (v2 §2)] If a marked block's text changes without its entry, or an entry's command changes without its block, then the check shall fail, and it ships with a fixture for each of the two cases.
- **AC-6.4** [I14 (v2 §2)] A block that shows command output shall be marked only when the examples job diffs the command's normalised output against the block and fails on a difference (the check ships with an output block that differs from the normalised output, which it must reject); otherwise output blocks stay unmarked.
- **AC-6.5** [AT-46 (v2 §18.2)] The examples job shall need no agent credentials and no paid service and shall run on pull requests from forks. A structural check fails when `.github/workflows/ci.yml` (which hosts the `site-build` job) or `.github/workflows/docs.yml` references `secrets.` for these jobs or uses `pull_request_target`; the fork pull-request run is a recorded maintainer inspection, not an automated check.

### FR-7 — Responsive, accessible layout (D-97)

- **AC-7.1** [D-97, v2 §15.1, AT-36 (v2 §18.2), G10 (v2 §18.3)] At viewport widths 390px and 1280px, every published page shall have a document scroll width no greater than the viewport width, and a check shall assert this against every rendered page of the built site, driven by a pinned headless-Chrome Node script in the one carved-out directory of AC-7.6 (OQ-5), including the longest (`user-guide.html`); the check ships with a fixture page containing a `pre` wider than the viewport outside its scroll container, which it must reject. The check also fails on any element whose box passes the viewport outside an `overflow-x: auto|scroll` container, so `overflow-x: clip` on `html` or `body` cannot hide an overflow; its fixture is a page with that clip.
- **AC-7.2** [D-97, v2 §15.1, AT-36 (v2 §18.2)] Interactive targets (nav links, the search control, the sidebar toggle, copy buttons, recording chapter buttons) shall be at least 44px by 44px at 390px. The headless-browser pass asserts this and the first-viewport position of AC-2.1, and NFR-3's weight, on the built landing page.
- **AC-7.3** [D-97, v2 §15.1, AT-36 (v2 §18.2)] Body text and links on both surfaces shall meet 4.5:1 contrast and large text and UI parts 3:1, with Star light `#00829d` on Paper (4.08:1) used only for large text and UI parts and links and small text on Paper set in Ink with a Star underline or marker (OQ-4), and a check shall assert the foreground and background pairs computed from the rendered pages (not a hand-kept list of token pairs) and reject a fixture pair below the threshold and a fixture page using an undeclared pair.
- **AC-7.4** [D-97, v2 §15.1, AT-36 (v2 §18.2)] Demo images and their captions shall fit the column with the caption below the image, and every recording shall carry a text alternative that names what it shows and that it is scripted. The user guide's three autoplaying GIFs (`docs/user-guide.md:39-46`) shall be served as static posters with the recording started on request, or replaced by the AC-2.2 player.
- **AC-7.5** [D-97, v2 §15.1, AT-36 (v2 §18.2)] Where the visitor prefers reduced motion, no recording or element shall animate unprompted, and a static poster stands in for every GIF; the landing page stays Night and the docs pages stay Paper whatever the visitor's colour-scheme preference.
- **AC-7.6** [D-97, G10 (v2 §18.3)] The implementing change shall add to `.claude/rules/harness-scripts.md` an explicit carve-out for exactly one browser-driver directory under `scripts/ci/` (named in the design), allowing Node there and nowhere else under `scripts/**`, with the evidence for it; the driver's tests run only in the `ci.yml` site-build job after `npm ci` and never skip when Chrome is missing, and every other new check is Bash or Python standard library with fixtures gated by `CI OK`'s harness job. This spec does not edit the rule; the carve-out is a requirement on the harness task (OQ-5), and `scripts/ci/lint-agent-harness.sh` passes with it.

## Non-Functional Requirements

- **NFR-1** [D-97, G10 (v2 §18.3), I14 (v2 §2)] The site makes no request to a third-party origin and ships no analytics (checked by AC-1.5: off-origin requests and the script allow-list).
- **NFR-2** [N1] The Jekyll build step's duration and the built site's total size are recorded in the pull request before and after, so the card's "revisit if build speed hurts" has a number.
- **NFR-3** [G10 (v2 §18.3)] The landing page's transferred weight excluding the hero recording is at most 500 KB, and the hero recording is not fetched before the visitor starts it (`preload="none"` with a poster); today the page loads two GIFs of 1.67 MB and 1.24 MB (`ls -l docs/demos/*.gif`).
- **NFR-4** [D-97, G10 (v2 §18.3)] Site content is generated only by `actions/jekyll-build-pages` and the existing mirror front-matter injection; steps that check sources or the built `_site` are allowed. Check fixtures are built by a separate check build that reuses the layouts and is never deployed, indexed or linked from the site. Jekyll plugins stay within the GitHub Pages allow-list, and any new GitHub Action is pinned to a full SHA (`.claude/rules/github-workflows.md`). Fixtures never live under `docs/`. Fixtures that need no Jekyll are static files under `scripts/ci/tests/fixtures/` checked by tests gated by CI OK; Jekyll-rendered fixtures are built and checked only in the docs workflow.
- **NFR-5** [D-97, G10 (v2 §18.3)] The built search index is at most 300 KB uncompressed (accepted as written under OQ-10; the maintainer may change it), and a build check fails above it and ships with an oversized fixture index; the design chooses what to exclude (AC-4.1).
- **NFR-6** [D-97, G10 (v2 §18.3)] The Node driver of AC-7.6 ships with a committed lockfile and `npm ci`, `actions/setup-node` pinned by SHA with no dependency cache in the deploying workflow, an npm entry in `.github/dependabot.yml` with the repository's 7-day cooldown, a stated browser source (the runner's preinstalled Chrome with its version recorded, or a checksum-verified download) and new rows in `docs/automation.md`; before the driver is added, the licence of every package in its resolved tree is checked against the allow-list in `.github/workflows/dependency-review.yml` (`grep -n "allow-licenses" .github/workflows/dependency-review.yml`), and if any is not on it the task stops and reports to the maintainer, never widening the allow-list itself. Vendored font or search-library files get the same source, version and SHA-256 record as AC-1.4.
