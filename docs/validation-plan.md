# Focused validation plan

**Decision: validate dependable native-agent delivery before expanding the platform.**
This is a feasibility plan, not evidence of a performance advantage. The proposed
window is **22 October–4 November 2026: ten working days**, including readiness,
recruitment and reporting. Missing prerequisites do not move the end date silently.
The final decision is continue to a separately designed study, simplify, stop, or
report blocked/inconclusive with the missing evidence.

The operator selected this delivery focus. Formal changes to product objectives
and backlog selection are separate signed proposals. This plan does not advance
the current product stage, qualify a route, change an invariant, or authorize
inference, publication, outreach or spending beyond an existing applicable grant.

## User and hypothesis

The initial user is an individual developer or small trusted team doing repository
maintenance across interruptions and repeated sessions. The useful outcome is an
independently accepted change with less reconstruction, checking and supervision.

The hypothesis is that preserved native context, grounded dependency references
and prompt independent acceptance can reduce whole-task delivery time without
lowering acceptance or introducing important defects. The native harness continues
to own its reasoning/tool loop. Multiple agents are not a prerequisite.

Current evidence does not establish this hypothesis. The [measured self-hosting
pilot](dogfood/0003-measured-self-hosting.md) contains one dependent development
component; direct native execution was shorter and acceptance scheduling differed.
Current admission, isolation, checks and receipts do not themselves implement
native-session continuity or selective context. External coordinator reviews are
not evidence that the shipped runtime autonomously improves output quality.

## Scope and critical path

Focus on one explicitly described **Claude Code/Linux** bundle, one writer,
independent acceptance and truthful recovery. Preserve native instructions,
permissions, account settings and the full original task contract. Keep optional
learning and external telemetry off. Broader UI/theme work, additional platforms
and harnesses, plugins, adaptive routing, parallel construction and Herdr expansion
are deferred during this cycle. Preserve existing candidates and evidence; essential
CI and correctness repairs may finish under their own finite task budgets.

| Order | Work and owner | Dependency or limit |
|---|---|---|
| 1 | Route/evidence audit and frozen task catalogue; evaluation coordinator with an independent reviewer | Immediate next task. Check actual native version, tool availability, identity, funding posture, supported resume surface and existing measurement coverage before any assigned run. |
| 2 | Reproducible direct-native and current-wrapper pilot; evaluation coordinator | Locked source/task/checks, parity audit and prospective protocol review. Do not wait for a platform rebuild. |
| 3 | One minimum continuity/context candidate if the bottleneck evidence warrants it; core/adapters implementer | Separate bounded task/spec and qualified surface, followed by a separately registered contrast. No hidden changes to the current-wrapper comparison. |
| 4 | Consented usability sessions and repeat use; volunteer participants with the coordinator | Recruitment and consent are prerequisites. These observations do not enter the controlled-pair estimate. |
| 5 | All-assigned report and product recommendation; independent evidence reviewer | Include failures, missingness, elapsed budgets and defect-window status even if the result is blocked or disappointing. |

Existing planning dependencies remain visible:

- **MH-12** earns strict subscription-only qualification; the current
  `subscription-declared` posture is user-declared and unverified. A successful
  sign-in does not prove overage prevention. Unknown mandatory evidence blocks
  the affected route or claim; do not change the billing posture to pass a trial.
- **MH-15** covers continuity and cross-harness handoffs. Its current card requires
  S1, MH-21 and two independent route qualifications. A proposed same-harness
  experiment needs an explicit scoped design; this plan does not waive those
  prerequisites or claim the whole card complete.
- **MH-24** requires S1 and MH-15. A source index in a task packet is not the
  implemented dependency graph or stale-evidence invalidation capability.
- The merged **protected-acceptance** slice supplies existing contract/evidence
  foundations. Its presence does not establish complete S1 or native qualification.
- **supervisor-attachment-control** remains in progress. Existing owned-entry
  candidate work must pass its independent acceptance before use; it is not a
  prerequisite for a comparison using an already supported legacy run path.

The day-one audit produces an explicit usable experimental bundle or a blocked
readiness report. An admitted unqualified route can only be described at its
actual experimental scope; it cannot satisfy a claim requiring qualification.
Do not spend the window repeatedly probing a known unavailable provider.

## Pilot design: fixed before assignment

Prepare **twelve paired tasks across at least three external, publicly licensed
repositories**. Select realistic maintenance work and its task-family taxonomy
before results. Check repository authority, license, immutable input revision and
protected acceptance fixtures. Existing MYTHHELM tasks and previously examined
fixtures remain development evidence, not fresh holdout observations.

Use the strongest reasonable direct Claude workflow, including ordinary scripts,
skills and native session features. Hold original task, source, model, effort,
effective tools/configuration/permissions, environment, cache/history policy,
budget and independent acceptance constant. An intentionally limited direct arm
is not a useful baseline. Provider cache occupancy and internal effort that cannot
be observed remain limitations rather than asserted parity.

Freeze assignments and balanced order through the existing
[measured-delivery procedure](harness/measured-delivery.md#controlled-comparisons).
Before the first pilot assignment, designate exactly one decision contrast and
allocate the twelve-pair budget across it and any diagnostics. Begin with a
current-wrapper comparison; a later context or continuity treatment needs a
distinct prospective protocol with its differences declared. If that candidate is
the designated decision contrast and cannot become ready, report it blocked;
do not substitute the diagnostic contrast after seeing its results. Only the
designated contrast governs the continuation target. No pooling or choosing the
best observed contrast is allowed. Another protocol does not replenish the cycle
budget. No assignment or live trial is created by this document.

Each assigned arm has one native start, at most twenty minutes of native execution
and a **thirty-minute complete-acceptance ceiling**. Reserve verification/review
capacity first. Start equally budgeted independent acceptance promptly when each
candidate is ready. Bind acceptance to the exact source, contract, evaluator and
environment. Required integration, final checks, review and any contract-required
CI belong inside the thirty-minute endpoint and canonical accepted
`wall_seconds`, as the shared measurement procedure requires. Optional external
publication and post-acceptance closeout are separate. Unequal review queues must
not manufacture a speed result.

The primary endpoint is mean **restricted time to independent acceptance**:
accepted within the ceiling uses observed time; a failed, blocked or timed-out
assignment scores the ceiling. Keep every assignment in the denominator. This
score does not say failed work finished at the ceiling. Retain actual cleanup
duration and unresolved ownership separately. No hidden reruns, dropped failures
or optional continuation until a favorable result appears.

Pairs sharing a repository **or** task family form transitive dependent
components, as implemented by the existing analysis. Three repositories can
still yield one effective component. Do not invent unique family labels to
inflate independence. This small pilot is descriptive and cannot establish
population superiority or equivalence.

For the designated contrast, calculate each arm's mean restricted time within
each component, then average those component means with equal component weight.
Let the resulting direct-native mean be D and MYTHHELM mean be M. The descriptive
gain is `(D - M) / D`; an unavailable or zero D leaves the gain undefined and the
target unmet. Use the existing analyzer's component weighting, not a pooled mean
that overweights repeated tasks from one repository or family.

## Costs, reliability and coverage

Record stage time for native work, verification, review, queueing and closeout;
native starts, retries, denied/unavailable tools, unexpected errors, reviewed
defects and human interventions. Separate expected red-first failures, candidate
defects, infrastructure failures and unresolved causes. A passing rerun does not
erase its earlier failure.

Keep input, output, cache-read and cache-creation counters separate, with their
reported/observed scope. Include native children, preparation, summaries, repairs
and coordinator/reviewer work where measurable. Missing coverage stays unknown;
native-only counters cannot establish a whole-task token saving. Do not sum
overlapping cache categories or call a retail estimate an account charge.

Measure active human minutes explicitly, separately from passive waiting and
queue time. Do not derive human effort from transcript duration. Report missing
measurements and token-category tradeoffs even when the primary endpoint improves.
All candidates receive the same defect rubric and at least seven days of follow-up.
If that window is still open at the decision date, mark it open and withhold the
affected quality or publication conclusion.

## External use and consent

Target **five consenting external testers**; require **at least three to complete
a voluntary second live use** for the repeat-use criterion. Current recruited
testers: **zero**. Synthetic demos, expressed interest and an invitation sent are
not completed live uses. Missing participants are not successes.

Ready-to-share participant checklist:

1. Choose a small real task in a repository you are authorized to use. Review the
   exact supported/experimental route and its limitations first.
2. Use your own authorized native account and settings. Review the task's finite
   budget, effective hooks/tools/data destinations and paid-continuation posture.
3. Preview and consent to minimal local observations and any separately scoped
   export. Core operation does not require external telemetry or raw capture.
4. Record active setup/recovery/review effort, actual result, confusing moments
   and whether you would choose the tool for another task.
5. A second use is voluntary and separately admitted. You can decline or stop;
   keep permissions, export, retention and erasure choices explicit.

This is a recruitment kit, not authorization to contact people. Do not publish
raw prompts, source from private repositories, transcripts, account identifiers
or participant identities. Publish only consented, reviewed aggregates.

## Budget, decision and stopping rules

The proposed cycle has at most **38 native starts**: 24 assigned pilot arms,
four separately scoped prototype-authoring starts, and ten observational tester
uses (up to two each). Every start requires applicable current authority and
normal admission; this planning ceiling grants no spending or configuration
trust. Each start is capped at twenty minutes, with separate finite stop/ownership
reconciliation. Do not substitute metered inference or renew expired authority.
Existing outside-cycle dogfood work stays separately recorded, not a pilot win.

Advance only to a separately designed confirmatory study when all these
**feasibility targets**, fixed before the new results, are met:

- At least **20% lower descriptive component-weighted mean restricted time to
  acceptance** in the designated contrast versus its matched direct-native
  baseline, using `(D - M) / D` and the fixed ceiling/all-assigned rule.
- No lower all-assigned acceptance, no observed new critical/important accepted
  defect, and no safety violation. These observations do not prove equivalence.
- Auditable parity, complete time/outcome accounting, explicit usage missingness
  and token tradeoffs, and the external repeat-use criterion above.
- A practical independently reviewed sample/power plan and resources for a fresh
  holdout. The pilot cannot become its own holdout; existing conservative bounds
  may require more independent data than the available budget supports.

If benefits are limited to a narrower workflow, propose a smaller CLI/plugin or
workflow package. If readiness, recruitment or coverage is unavailable, record
blocked/inconclusive and its exact consequence. If useful benefit is absent,
stop the expansion hypothesis. Any extension requires a new recorded decision;
neither extra features nor another pilot are automatic next steps.

The end artifact is an all-assigned report and a **continue / simplify / stop /
blocked** recommendation, plus a separately filed product decision. General
README/site advantage claims require the existing
[publication criteria](benchmarks.md#publication-criteria), reviewed uncertainty,
independent sampling, completed defect observation and a protected holdout.
